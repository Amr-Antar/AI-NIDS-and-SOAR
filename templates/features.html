Layer 1 — Detection Engine

Classification pipeline capabilities

Five-class intrusion classification

Every connection record is classified into one of five categories: Normal Traffic, Denial of Service, Reconnaissance/Scanning, Privilege Escalation, or Credential/Access Abuse. Each classification is accompanied by a per-class probability distribution and a confidence score used to drive all downstream routing decisions.

Confidence-gated unknown suspicious escalation

When the ensemble's highest class probability falls below the detection threshold, the connection is routed as "Unknown Suspicious Behavior" rather than assigned an unreliable category. Uncertain events are preserved for analyst review — never silently dropped, never misattributed to a class the model isn't confident about.

SMOTE oversampling for rare attack families

U2R and R2L attacks represent under 1% of NSL-KDD traffic. Without targeted oversampling, the model defaults to majority-class behavior and effectively misses these attack families. SMOTE generates synthetic minority-class samples during training so rare but high-severity families receive full detection coverage.

Mutual information feature selection — 30 of 41 dimensions

Not every feature in a network connection record carries meaningful signal for distinguishing attack families. Mutual information scoring ranks all 41 NSL-KDD features and selects the 30 most discriminative, reducing inference noise and improving generalization on traffic patterns not seen during training.

Three algorithms evaluated — one ensemble deployed

Logistic Regression, Decision Tree, and Random Forest were each trained and benchmarked independently on the same validation split. The Soft Voting Ensemble combines all three, consistently outperforming every individual algorithm on precision, recall, detection rate, and false positive rate across all five classes.

Automated preprocessing pipeline

Uploaded CSV files are processed through the same conditioning pipeline used during training: header validation, type normalization for categorical and numeric fields, missing value imputation, and feature selection — applied automatically so the model always receives properly structured input without manual preparation.

Layer 2 — Analyst Response

What the analyst can do with each detection

Source IP retained for every classified record

Every prediction row preserves the originating source IP address alongside the risk level, confidence score, and a plain-language decision reason. Analysts have the full context needed to investigate, validate, or escalate any event without leaving the dashboard or switching tools.

Manual block and automated high-confidence blocking

Analysts can block any source IP directly from the detection table. Critical high-confidence threats meet an automated blocking policy that fires without requiring manual intervention. Both manual and automated blocks are recorded in a full audit log with decision context and timestamps.

Visual threat alert with immediate response controls

When a dangerous or unknown event is detected, a modal appears immediately after upload showing attack type, source IP, confidence score, and risk level — with direct Block, Ignore, and View Details controls. The analyst gets the critical information before anything else on the page.

Persistent threat banner for session-level awareness

When an uploaded file contains threats, a persistent banner at the top of the dashboard summarizes the highest-risk detection and links directly to the results table. Threat context stays visible across the session without requiring the analyst to scroll back up or remember what was flagged.

Block notes with archiving and inspectable history

The block and unblock activity log can be cleared from the live view after review. Cleared entries are moved to a secondary archived history rather than deleted, preserving the full audit trail for compliance or retrospective analysis. Permanent deletion of archived history requires explicit admin confirmation.

Unblock workflow with reason capture

Every unblock action requires an analyst-entered reason before it is confirmed. This prevents accidental removals and ensures the audit trail always reflects the rationale behind every change to the block registry — block decisions and reversals are both fully documented.

Layer 3 — Feedback and Adaptive Learning

How the system improves over time

Per-prediction feedback with four classification states

Analysts can mark any prediction as Correct, False Positive, False Negative, or Needs Review — with an optional corrected label. Feedback is captured inline in the detection table and stored immediately, building a growing record of analyst assessments tied to specific prediction records.

Canonical label normalization before storage

Corrected labels entered by analysts — in any form — are resolved to their canonical equivalent before being written to the database. This prevents label inconsistency from accumulating across feedback cycles. Inputs that cannot be confidently resolved are rejected with an explicit warning rather than stored as ambiguous training signal.

Background retraining with live model reload

Retraining runs as an async background process using the NSL-KDD benchmark dataset. The dashboard remains fully operational throughout. When the cycle completes, the model is reloaded in memory and the Analysis page reflects the updated performance metrics on the next load — no restart or manual intervention required.

Feedback export for downstream integration

All analyst corrections are available as a downloadable CSV containing the original prediction, confidence score, feedback label, and normalized corrected label. This structured export can be used for audit purposes, manual data review, or as supplementary input to future training cycles.

Layer 4 — Performance Analysis

Full training transparency on the Analysis page

Per-class detection metrics from held-out test split

The Analysis page surfaces per-class precision, recall, and F1-score computed on a completely held-out test set — not the training data and not cross-validation averages. This gives an honest picture of how the model performs on each attack family when it encounters records it has never seen before.

5-fold cross-validation stability evidence

Cross-validation scores for all five training folds are shown individually alongside the mean. Consistent scores across all five folds confirm that the model's performance is not an artifact of one favorable data partition — it generalizes across different subsets of the training distribution.

Algorithm comparison across all three models

Performance metrics for each individual algorithm — accuracy, F1, false positive rate, detection rate — are charted alongside the final ensemble. This makes the case for the ensemble visible: analysts can see exactly where the combination of algorithms outperforms every individual component.

Live stored prediction distribution

A doughnut chart and breakdown table show the cumulative distribution of all stored predictions across every upload session. These values are read from the live database on each page load — they reflect the current state of the prediction store, not a cached snapshot.
