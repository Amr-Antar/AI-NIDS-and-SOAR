Design Philosophy

Why Waqqas was built this way

From raw records to actionable security decisions

Most IDS implementations stop at a classification output. Waqqas treats that as the starting point. Every prediction feeds into a structured analyst workflow — source IP visibility, risk scoring, alert generation, block controls, and feedback capture — giving each detection decision a clear path forward.

Bridging detection performance and operational behavior

Waqqas is engineered to behave like a real intrusion detection system rather than a research experiment. Persistent state, alert-first interface design, confidence-aware escalation for uncertain events, and a retraining path with internal label integrity give it the operational characteristics that matter in practice.

Detection Architecture

Engineering decisions behind the detection engine

Soft Voting Ensemble over single-model output

Three independently trained algorithms — Logistic Regression, Decision Tree, and Random Forest — were evaluated on the same validation split before being combined. The ensemble consistently outperforms every individual algorithm on precision, recall, detection rate, and false positive rate.

SMOTE for rare attack families

U2R and R2L attacks represent under 1% of NSL-KDD traffic. Without corrective oversampling the model defaults to majority-class prediction. SMOTE generates synthetic minority-class samples during training to force first-class detection across all five attack categories — including the rarest and most dangerous ones.

Mutual information feature selection

SelectKBest with mutual information scoring identified the 30 highest-signal features from the full NSL-KDD 41-feature set. This reduces inference overhead, removes noisy dimensions, and improves generalization when the model is applied to traffic patterns it has not directly seen during training.

Canonical label system for safe retraining

Every label used internally — in training, prediction, storage, feedback, and retraining — maps to one of five canonical classes. Analyst-entered corrections pass through a normalization resolver before storage, preventing label drift from accumulating across feedback cycles and corrupting future training pipelines.

Operational Behavior

How the system behaves at runtime

Confidence-gated unknown escalation

When the ensemble's highest class probability falls below the configured threshold, the connection is classified as "Unknown Suspicious Behavior" rather than assigned an unreliable attack label. Analysts are never presented with a high-confidence prediction the model is not actually confident about.

Source IP-aware automated response

Every classified record retains its source IP. High-confidence critical threats trigger automatic IP blocking. Analysts can block or unblock any source directly from the detection table. Every action is logged with a timestamped, reason-annotated audit note.

Presentation-layer label transformation

The interface shows refined, human-readable attack names. Internally, the system always uses the original canonical labels for inference, storage, and retraining. The transformation is strictly presentational — it never affects the classification pipeline or the integrity of stored data.

Background retraining with live model reload

Retraining runs as an async background process — the dashboard remains fully operational during the cycle. When training completes, the model is hot-reloaded in memory. The Analysis page reflects the updated metrics immediately on the next page load.
